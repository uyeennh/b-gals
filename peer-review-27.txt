Main.go is a good entrypoint  
 - all goroutines and all the channels are initialized and passed in main so that you can
  see the projects dependencies without having to open other files.  

The modularity is good, all the modules have a clear central purpose and none of them intervene with others responsibilities.

There is a good coherence in the project and across the modules - f.ex. worldviewmanager has a wide interface with 7 channels,
but all of them are relevant to the modules purpose

Config.go is clean way to avoid magic numbers and make the code even more readable. 

The Standalone/Networked mode being handeled entirely within WVmanager
(not letting ElevatorDriver and OrderDispatcher aware of network state)
is a clean design to make the modules loosely coupled.

The FSM functions are small and concrete - and that is also a trend acorss the
rest of the code. Each function does one thing and that makes it easy to verify if correct and 
easy to continue to use if you were to make the project more advanced

The information flow is consistent in one direction through the system
(buttonpress to WorldView to orderdispatcher to elevatordriver) which makes it easy to trace and debug.

main.go does not give a full picture of the system since the network channels
and button polling are created inside the distributor, not in main. Therefore if 
you read main you cant see all the dependencies without opening other files. 

The distributor handels to many responsibilities, button polling, network broadcast,
order merging, lamp updates and order assignment happens in the same goroutine. This 
reduces the modules cohesion and make it harder to change without unintended sideeffects. 

The FSM in fsm.go is large and complex, which makes it hard to see if the obstruction 
handeling is correct or not.
